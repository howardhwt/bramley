# DS and PSP on the Brick: how other systems do it

Research for [ds-psp.md](ds-psp.md), 2026-11-05. It covers how the firmwares that run on the TrimUI Brick handle the PSP's analog stick and the DS's two screens and touch screen. Most claims come from the firmwares' own config files and scripts on GitHub, read at their default branches on 2026-11-05, and from TrimUI's own SD card package. Claims marked "unverified" come from reviews, forum posts or inference, and were not checked against a config file or source.

## Summary

### What most systems do

- **PSP stick.** Every system that runs PSP on the Brick ships standalone PPSSPP, not the libretro core. None of them remaps the PSP stick inside PPSSPP's own config for the Brick. Their `controls.ini` binds the PSP stick to real stick axes only, and they rely on a system-wide switch that turns the D-pad into a virtual left stick. That switch is a flag file read by TrimUI's input daemon, `trimui_inputd`: touching `/tmp/trimui_inputd/input_dpad_to_joystick` (with `input_no_dpad`) makes the D-pad report as a stick. Stock TrimUI puts it on the FN switch through its FN Editor, Knulli puts it on Function+Select, spruceOS puts it on the FN switch, and muOS uses the same file name under its own input daemon with an L2+R2+A hotkey. One NextUI pak (ben16w/minui-psp) uses PPSSPP's own `AxisSwap` key on R2 instead. No system ships per-game stick profiles for the Brick.
- **DS emulator.** All of them use a DraStic build with a hooking library for layouts and the stylus, except spruceOS. On the Brick that hook is trngaje's Advanced DraStic, in Knulli, CrossMix, muOS and the NextUI DS pak. Stock TrimUI ships its own patched DraStic ("Drastic SDL2 MOD"). spruceOS now defaults to DSperate on the Brick's chip. DSperate is a new GPL-3.0 emulator that reimplements DraStic's techniques and needs no BIOS, and it already has a NextUI pak. Nobody defaults to melonDS or DeSmuME on the A133P.
- **DS screens.** Every DraStic-based system offers stacked, side by side, single screen with swap, and large plus small layouts, with a button to swap screens and a hotkey to cycle layouts. Defaults differ: CrossMix appears to default to side by side, muOS to a large plus small layout, and DSperate to stacked.
- **DS touch.** Every system uses an on-screen stylus cursor. With no stick, the cursor is driven by the D-pad in one of two ways. In the first, a toggle switches the D-pad between game input and the cursor (Advanced DraStic L2, Knulli Function+Select). In the second, a held button turns the D-pad into the cursor while it is held (DSperate: hold R2 to aim, L2 to tap). A shoulder button or A taps.

### What Bramley should copy

1. Use the `trimui_inputd` D-pad-to-stick flag as the base mechanism for PSP, because it is what stock, Knulli and spruceOS use, it works under any emulator, and Bramley already has the code. `emulateJoystick()` and `disableDpad()` exist in `workspace/tg5040/libmsettings/msettings.c` but nothing calls them, and `workspace/tg5040/platform/platform.c` already drives the same daemon for turbo. Bramley must clear the flag when a game exits, as stock `premainui.sh` and spruceOS do, or the launcher's D-pad stops working.
2. Make the PSP mode a per-game setting with a default per game, and offer both a hold modifier and a toggle. No other system does per-game profiles, and Howard's one PSP game (a fighter) wants the D-pad while 3D games want the stick.
3. If Bramley uses PPSSPP standalone, also bind PPSSPP's own axis swap key, which exists as `AxisSwap` in 1.17 and as hold and toggle variants in current master. If it uses the libretro core, add a "D-pad as left stick" hold modifier in minarch's input layer instead, so the in-game menu can show and remember it.
4. For DS, measure DSperate first. It is GPL-3.0, so it can ship on the card, it needs no BIOS, it already has a NextUI pak with a NextUI-style pause menu, and spruceOS trusts it as the default on this chip. Keep "bring your own Advanced DraStic" as the fallback.
5. Copy DSperate's touch model, a held button that turns the D-pad into the stylus plus a second button that taps, because it has no hidden mode to get stuck in. Offer the Advanced DraStic toggle as an option.
6. Offer four DS layouts that fit 1024x768 at whole-number scales: stacked at 2x (512x768), side by side at 2x (1024x384), single screen at 4x (1024x768), and large plus small with the large screen at 3x (768x576) and the small one at 1x (256x192) beside it, which fills the 1024 width exactly. Put swap screens on one button, cycle layouts on MENU plus a direction, and remember both per game.

Notes on Question 1:

- In PPSSPP, axis swap swaps the D-pad and the left stick in both directions, so while it is on, the D-pad drives the stick and the stick drives the D-pad. The hold variant applies only while its key is held. This is in `ControlMapper::SwapMappingIfEnabled()` in PPSSPP's source: https://github.com/hrydgard/ppsspp/blob/master/Core/ControlMapper.cpp.
- PPSSPP also has "Analog limiter" (`VIRTKEY_ANALOG_LIGHTLY`), which several of these configs bind (`Analog limiter = 1-60`). On a D-pad driven stick it would give a walk speed. Source: https://github.com/hrydgard/ppsspp/blob/master/Core/KeyMap.cpp.
- Bramley's NextUI base already writes to `trimui_inputd` for turbo buttons (`PLAT_toggleTurbo()` in `workspace/tg5040/platform/platform.c`), and `workspace/tg5040/install/boot.sh` kills `trimui_inputd` only after the launcher exits. That suggests the daemon runs under Bramley, but whether the D-pad flag reaches PPSSPP and minarch as `ABS_X` and `ABS_Y` on the Brick is unverified.
- DSperate has a related feature for DS games: about 70 games get analog control through shocoman's Circle Pad patches (https://github.com/beebono/DSperate). That is for DS, not PSP.

Notes on Question 2:

- Advanced DraStic's own key table is: L2 toggles stylus and D-pad, R2 swaps screen 0 and 1, MENU opens settings, SELECT is the hotkey, SELECT+Left and SELECT+Right change the layout index, SELECT+Y changes theme, SELECT+B toggles blur and pixel mode, SELECT+L quick loads, SELECT+R quick saves. Source: https://github.com/trngaje/advanced_drastic. Its layouts are JSON files with screen rectangles and a background image, and there is a 1024x768 set made by resizing the 640x480 set. Source: https://github.com/trngaje/drastic_layout.
- steward-fu's original DraStic port numbers sixteen layouts at 640x480, from layout 0 (a full screen with a small transparent inset) through stacked (4, 5), side by side (6, 7), large plus small (8 to 11), and high resolution single (14). In its Stylus mode the D-pad moves the pen and A touches. Source: https://github.com/steward-fu/nds/blob/v1.8/README.md. steward-fu has since dropped support for these Chinese handhelds and tagged the last build `final-china-devices`: https://github.com/steward-fu/nds/releases/tag/final-china-devices.
- The libretro DS cores bring their own layouts and pointer. DeSmuME 2015 has `desmume_screens_layout` with top/bottom, bottom/top, left/right, right/left, top only, bottom only, quick switch and two hybrid layouts, plus an emulated pointer on a stick and R2 to tap. Source: https://docs.libretro.com/library/desmume_2015/. melonDS DS cycles a configurable list of layouts with "Next Screen Layout" (R2 by default), moves the cursor with the right stick and touches with R3. Source: https://docs.libretro.com/library/melonds_ds/. Both expect a stick for the cursor, so on the Brick they would need the D-pad-to-stick flag or a minarch modifier.
- There is a libretro core built around DSperate, thwonp/dsperate-lr (GPL-3.0). Its maturity and its speed on the Brick are unverified: https://github.com/thwonp/dsperate-lr.

## Performance notes on the A133P

- **DraStic.** Every Brick firmware that ships a DS emulator defaults to a DraStic build or DSperate, which suggests DraStic is the known-good option on this chip (inference). On an RK3566 with four Cortex-A55 cores, DSperate's author measured DraStic rendering a DS frame in 2.98 ms, about 5.6 times real time. That is on a faster chip than the A133P's A53 cores. Source: https://github.com/beebono/DSperate/blob/main/docs/techniques/00-method-and-measurements.md.
- **DSperate.** It is built for and measured on the RK3566 (A55), and spruceOS makes it the default on the A133P Brick and the Smart Pro, which suggests it is fast enough there (inference, no measured numbers for the A133P). Sources: https://github.com/beebono/DSperate, https://github.com/spruceUI/spruceOS/blob/Development/Emu/NDS/config.json.
- **melonDS and DeSmuME 2015.** No firmware defaults to either on the A133P, and no measured numbers on this chip turned up (unverified). The libretro docs say DeSmuME is software rendered only, that its interpreter is much slower than its JIT, and that some games such as Golden Sun: Dark Dawn run very slowly even on desktop. Source: https://docs.libretro.com/library/desmume_2015/.
- **PPSSPP.** No measured numbers for the A133P turned up. A muOS community post (by a user, not the muOS team) says that on the Brick "you're largely limited by the device's hardware, thermal constraints, and game-specific quirks", and suggests 1x PSP resolution and frameskip 1 with auto frameskip. Source: https://community.muos.dev/t/ppsspp-performance-optimisations/323. Stock TrimUI and CrossMix both offer OpenGL and Vulkan launchers plus "performance" launchers that raise the CPU frequency, which suggests the backend choice is game by game (inference). Stock's Vulkan config ships `InternalResolution = 2` and `FrameSkip = 0`. Sources: https://github.com/trimui/assets_brick/releases/tag/20241105, https://github.com/cizia64/CrossMix-OS/blob/main/Emus/PSP/config.json. Reviews describe PSP on the Brick as playable for only part of the library and note that games that need the stick suffer without one (unverified, secondary): https://retrohandhelds.gg/trimui-brick-review/, https://www.joeysretrohandhelds.com/reviews/trimui-brick-review/.
- **GPU quirks.** Knulli patches PPSSPP for the A133's PowerVR GE8300 (`glStringi` and `glCopyImageSubDataEXT` workarounds), and spruceOS runs PPSSPP with `SDL_VIDEODRIVER=mali` and a `setalpha 0` helper on PowerVR TrimUI devices. Sources: https://github.com/knulli-cfw/distribution/tree/knulli-main/board/batocera/allwinner/a133/patches/ppsspp, https://github.com/spruceUI/spruceOS/blob/Development/spruce/scripts/emu/lib/ppsspp_functions.sh.
